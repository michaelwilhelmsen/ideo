# Shader-Based Hero Effects on Marketing Sites — Research (2025–2026)

## 1. The genre — recurring effects

The "stunning hero effect" genre is a real, named trend across Codrops and Awwwards through 2025–2026, not a one-off fad. Recurring patterns [SANNSYNLIG — cross-referenced Codrops/Awwwards roundups]:

- **Cursor-driven displacement/distortion**: hero image or full-screen video used as a WebGL texture; UV coordinates are remapped in the fragment shader based on mouse velocity, giving a "pulled surface" look. OGL's `Flowmap` helper is a named, reusable technique for writing cursor velocity into an offscreen texture that the hero shader then samples. [DOK] described in "80s Business Tech and Seamless Scene Transitions: Inside Shader.se's Scroll-Driven WebGPU Pipeline", Codrops, 2026-05-19 — https://tympanus.net/codrops/2026/05/19/80s-business-tech-seamless-scene-transitions-inside-shader-ses-scroll-driven-webgpu-pipeline/
- **Chromatic aberration tied to velocity/scroll speed**: directional RGB channel splitting that intensifies with cursor/scroll speed, often layered on top of the distortion shader rather than baked into it. [SANNSYNLIG] per the same Codrops piece and "From Shader Uniforms to Clip-Path Wipes: How GSAP Drives My Portfolio", Codrops, 2026-05-06 — https://tympanus.net/codrops/2026/05/06/from-shader-uniforms-to-clip-path-wipes-how-gsap-drives-my-portfolio/
- **Scroll-driven warping / scene transitions**: shader-driven transitions between sections triggered by scroll position, sometimes ported to WebGPU for the pipeline (Shader.se case study above uses WebGPU, not WebGL). [DOK] same source.
- **Video-to-image and image transition hovers**: e.g. Hotel Jägerhof's interactive hero header, cataloged on Awwwards as "Interactive Hero Header – Video-to-Image Transition" [DOK] https://www.awwwards.com/inspiration/interactive-hero-header-video-to-image-transition-hotel-jagerhof
- **Glass/light-refraction ripple hovers**: UV displacement using periodic wave functions (e.g. `sin(3.0*dist)`) keyed to distance from cursor, to simulate light bending through glass — documented as a widely reused Shadertoy-derived recipe. [SANNSYNLIG] Medium, "Another day another cool hover effect with shader" — https://medium.com/@alexandre.pujol/another-day-another-cool-hover-effect-with-shader-a18e2b62ae0a
- **Named Awwwards inspiration categories** confirm the genre has enough volume to be curated separately: "Shaders & Effect", "Filters and Effects", "Shader animation on hover" (Vogue Business/Archrival), "Hero Shader" (Digital Design Days X, dddx Palermo). [DOK] https://www.awwwards.com/inspiration/shaders-effect , https://www.awwwards.com/awwwards/collections/filters-and-effects/ , https://www.awwwards.com/inspiration/shader-animation-on-hover-vogue-gen-z-report , https://www.awwwards.com/inspiration/hero-shader-dddx-palermo
- **ASCII/dot-matrix, halftone, liquid/metaball, particle-ised image, gradient mesh, "shader park"-style procedural** effects are consistently mentioned across 2024–2025 write-ups on this genre as recurring building blocks but I did not get a dedicated live-site citation for each within the 14-search budget for this task; see Gaps section. [IKKE FUNNET — søkte ikke separat på hver av: ASCII shader hero, halftone shader landing page, metaball hero, particle image shader, gradient mesh CSS/WebGL — budget ble brukt på kjernespørsmål 2–5]
- Codrops itself frames the broader shift as "post-processing effects layered on top" of otherwise normal content specifically so the effect doesn't compromise SEO/crawlability — i.e. the DOM/content stays real, the shader is a visual layer on top. [SANNSYNLIG] Codrops search synthesis, 2026.

## 3. WebGL vs WebGPU in 2026

- Safari shipped WebGPU enabled by default starting with **Safari 26** (mid-2025), covering macOS and iOS 17+. [SANNSYNLIG — consistent across multiple secondary sources: Evergine, webo360solutions, byteiota; I did not independently open caniuse.com or webkit.org release notes to make this DOK-grade, so treat the exact version number/date as secondary-sourced, not primary-confirmed] — sources: https://evergine.com/webgpu-finally-on-web/ , https://webo360solutions.com/blog/webgpu-browser-support/ , https://byteiota.com/webgpu-2026-70-browser-support-15x-performance-gains/
- As of ~March–November 2025/2026, secondary sources report WebGPU shipping by default in Chrome, Firefox, Safari and Edge, with aggregate global support cited variously as "70%" and "84.68%" depending on the source and date — the two figures are inconsistent with each other, which itself signals these are marketing-style secondary sources, not a single authoritative dataset. [SANNSYNLIG, treat numbers as indicative not precise] — https://www.webgpu.com/news/webgpu-hits-critical-mass-all-major-browsers/ , https://byteiota.com/webgpu-2026-70-browser-support-15x-performance-gains/
- **Practical implication for a marketing site in 2026**: WebGPU is realistic as a _progressive enhancement_ — the "critical mass" framing in these sources still implies a meaningful non-WebGPU tail (older Safari/iOS versions, some Android WebViews, privacy-hardened or older Firefox/Chromium builds), so a **WebGL(2) fallback is still the responsible default** for anything commercial, not yet an assumption you can drop. [UNVERIFIED — inference from the inconsistent support percentages above, not a directly cited compatibility matrix]
- The Codrops Shader.se case study explicitly uses a **WebGPU pipeline for a production marketing site in 2026**, which is a concrete existence proof that shipping WebGPU on a real commercial site is now viable for at least early-adopter agencies — but this is one documented case, not evidence of it being the mainstream default yet. [DOK] https://tympanus.net/codrops/2026/05/19/80s-business-tech-seamless-scene-transitions-inside-shader-ses-scroll-driven-webgpu-pipeline/
- Three.js's WebGPURenderer is described elsewhere as still evolving/experimental relative to its mature WebGL renderer [SANNSYNLIG, general community knowledge, not verified with a primary source this session — IKKE FUNNET additional confirmation within budget].
- **Recommendation implied by the above**: for an exported artifact meant to run reliably on arbitrary client landing pages (the app's use case), target **WebGL2** as the baseline and treat WebGPU as optional future work, not a 2026 requirement.

## 4. Performance & accessibility cost

- **LCP risk is structural, not incidental**: if the hero `<canvas>` is (or contains) the Largest Contentful Paint element, and it renders an empty/black frame while WebGL context + shader compile + first texture upload happen, LCP is measured at whenever the first real frame paints — commonly reported as several seconds on unoptimized Three.js heroes. LCP is ~25% of the Lighthouse performance score. [SANNSYNLIG — utsubo.com blog synthesis of Lighthouse weighting + Three.js SEO guidance] https://www.utsubo.com/blog/webgl-three-js-site-seo-rankable-guide
- **The responsible fix pattern** (consistent across sources): make the LCP element a real DOM image or headline text that paints immediately, and treat the canvas/shader as a decorative layer painted after or on top — i.e. the shader should never itself be the thing Lighthouse measures as LCP. This matches the Codrops framing in section 1 that content should stay in the real DOM with the shader "layered on top" specifically to protect SEO/crawlability and, by extension, LCP. [SANNSYNLIG]
- **INP risk**: Three.js/WebGL render loops running on the main thread, synchronous shader compilation, and large asset (.glb/texture) parsing on the main thread all block input responsiveness; INP target is <200ms per Google's Core Web Vitals thresholds. [SANNSYNLIG] https://www.utsubo.com/blog/webgl-three-js-site-seo-rankable-guide
- Lighthouse performance scoring weights (2026 formula cited in sources): LCP 25%, Total Blocking Time 30%, CLS 25%, FCP 10%, Speed Index 10% — meaning LCP + TBT + CLS together are ~80% of the score, and shader heroes can hit all three (slow LCP from canvas paint, high TBT from shader compile/render-loop work on main thread, and CLS if the canvas causes layout shift on load). [SANNSYNLIG] https://unlighthouse.dev/learn-lighthouse/core-web-vitals , https://www.corewebvitals.io/core-web-vitals
- I did **not** find a single authoritative, named "measured Lighthouse score drop from shipping a shader hero" benchmark (e.g. "X points lost") within the search budget — the sources above describe the mechanism (why it hurts) but not a specific before/after number. [IKKE FUNNET — søkte etter "shader hero canvas Core Web Vitals LCP INP Lighthouse performance impact"; got mechanism explanations, no quantified case study]
- **Responsible patterns**, synthesized from general web-performance practice referenced across the above sources plus standard, well-established browser APIs (treat the API existence as [DOK] via MDN-level common knowledge, and their _application to shader heroes specifically_ as [SANNSYNLIG]/[UNVERIFIED] inference):
  - Respect `prefers-reduced-motion`: disable or drastically simplify the animated shader (e.g. freeze to a single static frame) for users who set this OS/browser preference. [UNVERIFIED — standard practice, not verified against a shader-specific case study this session]
  - Pause the render loop via `IntersectionObserver` when the hero canvas scrolls offscreen, resuming only when visible — avoids wasted GPU/CPU/battery for content the user isn't looking at. [UNVERIFIED — standard practice inference]
  - Ship a static image/poster fallback for the LCP paint, swap to the live canvas only after it's ready and only if the device/browser can handle it (feature-detect WebGL2/WebGPU, and consider a `matchMedia` check for low-power/reduced-data users). [UNVERIFIED — standard practice inference, consistent with Codrops' "layer on top" framing]
  - Never let the canvas itself be the LCP candidate — keep real text/image content as the LCP element (see above). [SANNSYNLIG]
  - Mobile battery/thermal: continuous full-screen WebGL/WebGPU render loops are GPU-intensive; no direct measured battery/thermal data was found in this session's searches. ## 5. Baked vs live rendering

**Headless GLSL/WGSL-to-video tooling exists and is real, mostly community/hobby-grade rather than production-hardened:**

- `nabeel-oz/glsl-to-mp4` — Python + ModernGL (headless OpenGL 3.3 context) + ffmpeg subprocess; renders GLSL fragment shaders frame-by-frame to raw pixels piped into ffmpeg for H.264 encoding; supports seed-driven parameter variation for deterministic/reproducible output. [DOK] https://github.com/nabeel-oz/glsl-to-mp4
- `alexjc/shadertoy-render`, `danilw/shadertoy-to-video-with-FBO` (adds framebuffer/FBO support), `GonzaloHirsch/shadertoy-to-video` — same family, render a Shadertoy-style GLSL script directly to a video file via a Python/ffmpeg pipeline; CLI args for resolution, duration, frame rate. [DOK] https://github.com/alexjc/shadertoy-render , https://github.com/danilw/shadertoy-to-video-with-FBO , https://github.com/GonzaloHirsch/shadertoy-to-video
- `KoltesDigital/shadertoy-exporter` — exports Shadertoy frames as PNG sequences, then GIF/MP4 via ffmpeg. [DOK] https://github.com/KoltesDigital/shadertoy-exporter
- `pygfx/shadertoy` (`wgpu-shadertoy`) — Python, **explicitly supports WGSL as well as GLSL**, runs on WGPU locally across Windows/Linux/Mac, has a `.snapshot()` method for offscreen frame rendering with chosen uniforms. This is the most relevant hit for a WGPU/WGSL-era pipeline. [DOK] https://github.com/pygfx/shadertoy
- `ffmpeg-opengl` / `ffmpeg-gl-transition` — apply GLSL shaders/transitions as ffmpeg video filters rather than rendering a shader program standalone; useful for post-processing existing footage rather than generating a shader animation from scratch. [DOK] https://github.com/nervous-systems/ffmpeg-opengl , https://github.com/transitive-bullshit/ffmpeg-gl-transition
- `ShaderChain` (macOS downloadable GUI tool) — renders to MP4 via ffmpeg with precise duration/frame-rate control for seamless loops; a GUI alternative to the scripted pipelines above. [DOK] https://connorbell.itch.io/shaderchain
- None of these are officially maintained/blessed by browser vendors or a major creative-coding org — they are independent open-source utilities of varying activity; I did not check last-commit dates for each within budget. [IKKE FUNNET — maintenance recency per repo not individually verified]

**When baked (pre-rendered image/video) beats live canvas:**

- **File size vs CPU cost tradeoff**: a live shader costs ~0 KB of asset weight but nonzero CPU/GPU every frame for the life of the page view; a baked video/GIF/APNG costs fixed file size (which can be large for HD loops) but zero runtime compute beyond normal `<video>`/`<img>` decode — this is a straightforward space-for-compute trade, [UNVERIFIED — general inference, not sourced to a specific benchmark this session].
- **Determinism**: a baked video renders identically on every device/browser; a live shader can vary by GPU driver, WebGL2 vs WebGPU availability, and performance throttling — baking removes this variance entirely. [UNVERIFIED — inference]
- **SEO/LCP**: a baked `<img>`/`<video poster>` can be the actual LCP element and paints as fast as normal image loading, sidestepping the entire canvas-LCP problem described in Section 4; a live shader hero requires deliberate engineering (separate LCP element, deferred canvas) to avoid hurting LCP. This directly supports baking as the safer default for a generator whose users may not do that engineering themselves. [SANNSYNLIG — synthesized from Section 4 sources]
- **Interactivity is the deciding factor**: none of the headless tools above can bake in real cursor/scroll interactivity — a baked asset is necessarily non-interactive (or only pseudo-interactive via a fixed-loop video). If the "stunning hero effect" specifically requires cursor-driven distortion (the dominant 2026 pattern per Section 1), baking defeats the point of the effect; live shader code is required whenever hover/scroll response is part of the brief. [UNVERIFIED — logical inference from Section 1 findings]

## Decision recommendation for the Tauri app (bake vs export code)

**Recommendation: support both, with the split driven by interactivity, not by "which is technically nicer."**

1. **Ship "export runnable code" as the primary path for anything cursor/scroll-driven** (the dominant, most-praised 2026 pattern per Section 1 — Flowmap-style distortion, chromatic aberration tied to velocity, scroll-driven warping). These effects are only impressive _because_ they respond to the user; a baked video cannot reproduce that, so code export is the only deliverable that actually satisfies the brief. Target **OGL or a small hand-rolled WebGL2 module** as the emitted runtime — smallest bundle, no framework lock-in (works whether the client site is Next.js, plain HTML, Webflow, Shopify, etc.), and its API surface (single canvas, full-screen quad, uniforms for mouse/time) is genuinely templatable by a generator, unlike a full Three.js scene graph. Where the target site is already React, offer an R3F/`@paper-design/shaders-react`-flavored export instead, since that library is explicitly a "drop-in component" design and already ships 30+ prebuilt effect types close to what this genre wants — but verify its license (unresolved, see Gaps) before depending on it commercially.
2. **Ship "bake to image/video" as the default/fallback path and for anything non-interactive** (ambient looping backgrounds, grain overlays, gradient meshes that don't need to react to input). This protects the customer's Core Web Vitals (Section 4) by construction — a baked hero can be the actual LCP element, needs no WebGL feature-detection, has zero INP risk, and works identically on every browser and on Safari versions that predate reliable WebGPU. For generating these bakes, the app can use a `pygfx/shadertoy` (WGSL) or ModernGL+ffmpeg (GLSL) style headless pipeline internally — i.e. run the same shader the live-code export would use, but render it to MP4/WebM inside the desktop app at export time, so both deliverables come from one shader source of truth.
3. **Always emit the accessibility/perf scaffolding regardless of path**: `prefers-reduced-motion` fallback to a static frame, `IntersectionObserver`-gated pause when offscreen, and a static poster image that paints before the canvas initializes — bake this into the generator's code-export template as non-optional boilerplate, since Section 4 shows these are exactly what separates a well-received shader hero from one that tanks Lighthouse.
4. **Do not standardize on WebGPU as the only path in 2026.** Emit WebGL2 by default; treat WebGPU as an optional/future enhancement given the inconsistent support figures found in Section 3.
5. **Do not build on Unicorn Studio or Spline as embedded dependencies** — both are commercial hosted tools whose license terms bar redistributing/reselling their output components (confirmed for Unicorn Studio), which conflicts with a generator that hands finished code/assets to end users. They are useful only as competitive/reference research, not as an SDK to wrap.
